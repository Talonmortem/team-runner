# Восстановление Team Runner

## После перезагрузки, сбоя сети или Orca

1. Сначала сверь текущую попытку по командам из [SKILL.md](../SKILL.md). Зафиксируй проект, checkout, generation/epoch, пункт, attempt и зарегистрированные Run/Dispatch. Сопоставь `desired_state` с наблюдаемыми признаками. Если scope сменился, проверяй новые записи отдельно.
2. При паузе сохрани паузу. При остановке проверь завершение уже запрошенной остановки. Возобновляй исполнение только по явному разрешению. При здоровом runner и том же работающем Dispatch сохрани попытку, даже если UI пропал или сервис проекта требует восстановления.
3. При неизвестном состоянии сервиса сверь его через `team-runner service reconcile --project "$PROJECT_UUID"` и перечитай `service status`. Запускай подтверждённо остановленный сервис при наличии разрешения. После перезагрузки сервис может требовать запуска вручную. Даже в этом случае отдельно сверь состояние runner. См. [состояния сервиса](../../../../README.md#если-сервис-не-запустился) и [состояние и восстановление](../../../../README.md#состояние-и-восстановление).
4. Проверь `team-runner recovery status --project "$PROJECT_UUID" --workspace "$WORKSPACE_UUID"`. Сверь причину и время следующей проверки с полным статусом. При уже идущем восстановлении дай штатному механизму закончить проверку в пределах его бюджета. При сетевом сбое оцени `network` и `autonomy` в полном статусе. Включённая политика может продолжить ту же сессию в пределах бюджета. Если политика требует действия, сохрани точный blocker. См. [ограниченную автономность](../../../../README.md#ограниченная-автономность).
5. Переходи к замене агента или подготовке новой попытки, когда подтверждены остановка прежних ресурсов, их принадлежность и исход эффектов, а разрешение охватывает выбранное действие. Используй штатную процедуру для этой попытки и сохраняй её снимок. Для замены роли см. правила резерва в [настройках агентов](../../../../README.md#opencode-2-и-cloudru). Для штатного повтора и продолжения см. [управляющие команды](operations.md).
6. Сними свежий статус после действия. Подтверди работу по новым событиям, продвижению очереди с принятой работой или свежей записи выполнения нужного Dispatch. При ожидании укажи его причину и следующую проверку. Если доказательств мало, укажи недостающий факт, например подтверждение завершения конкретного Dispatch или квитанцию исходного запроса.

## Ожидание ресурса

- **Память.** При `waiting_memory` новые запуски ждут общей для Linux-пользователя очереди. Проверь причину, длительность и метрики в статусе, затем перечитай состояние. Сохрани попытку и место в очереди. См. [очередь запуска агентов](../../../../README.md#очередь-запуска-агентов-на-linux).
- **Тяжёлая проверка.** При `waiting_resource` проверь `verification.records`, события и связанное доказательство `RESULT.resource-wait.json`, если оно опубликовано для текущей попытки. Общая блокировка тяжёлых проверок защищает от одновременных запусков из разных workspace одного пользователя. Дождись подтверждённой очистки ресурсов предыдущей проверки и допуска. Свободный file lock сам по себе не подтверждает очистку процессов или портов. Сохрани связанные вопрос или эскалацию до штатного разрешения. См. [сериализацию тяжёлых проверок и checkpoint](../../../../README.md#verification-scope-and-coordinator-events).

## Терминал недоступен

Сверь привязку к текущему Dispatch, incarnation, владельца и checkout. `panel_status=orphaned` может означать потерю видимой панели при живом исполнителе. Для известного владельца открой терминал штатной кнопкой «Открыть терминал», если требуется просмотр. При `terminal_handle_stale` отличай основной mailbox от терминала агента. Восстановление mailbox имеет собственную процедуру и может сохранить Run, Dispatch и сообщения. См. [хранение и восстановление](../../../../README.md#хранение-и-восстановление) и [восстановление mailbox](../../../../README.md#token-speed).

Отсутствие панели, старого PID или вывода оставляет живость неподтверждённой. Для исчезнувшего локального терминала используй штатное подтверждение завершения исходного процесса вместе с записью запуска, совпадением владельца и incarnation, а также полным списком терминалов без исходного handle/PTY. После перезагрузки учитывай идентификатор загрузки ОС. При чужом incarnation или недоступном полном списке сообщи, какого подтверждения нет. Сохраняй журналы и блокировки.

## Неподтверждённый эффект

Сначала найди исходную квитанцию [по request ID](operations.md#потерянный-ответ). Различай UUID управляющей команды и UUID её эффекта в Orca. Для диагностики возьми исходный ID команды из квитанции или `blocker.facts.control_request_id`, а ID эффекта из `operations` полного статуса выбранной попытки. Возьми свежий scope и отдельный UUID для самой команды сверки:

```sh
team-runner reconcile --project "$PROJECT_UUID" --workspace "$WORKSPACE_UUID" \
  --generation "$GENERATION" --attempt "$ATTEMPT" --revision "$REVISION" \
  --request-id "$RECONCILE_UUID" --json
```

Сверка читает доказательства исходного эффекта. После неё перечитай исходную квитанцию и статус workspace. Исходная квитанция может остаться неизменной даже после снятия блокировки. Проверь итог по фактам. При `pending` или `absent` у неизвестного внешнего эффекта сохрани блокировку и недостающий факт. Для редкого явно разрешённого продолжения записанной операции см. правила `continue-operation` в [разделе состояния и восстановления](../../../../README.md#состояние-и-восстановление). Для таймаута самой сверки ищи её квитанцию по `RECONCILE_UUID`.

Для неизвестного запуска или продолжения сверь исходную квитанцию с текущим назначением координатора в `resources.agents`. Сопоставь Run, Task, Dispatch, терминал и incarnation с текущей попыткой. Если наблюдается новое назначение, проверь связь с исходным запросом и свежую активность. Для старой квитанции запуска при смене очереди действуют доказательства отзыва epoch, выхода более нового runner и закрытия его терминала, используемые `prepare-scope`.

## Изменилась зависимость текущего пункта

При живом runner сверь текущий пункт и сохранённую выборку `options.items` с `item-contract.json` из точного каталога попытки и актуальными goal/feature `Tasks.json`. Проверь, появилась ли прямая зависимость, которой не было в снимке. Для SHM такой случай — текущий WA-GATE и новый обязательный WA-G04. Проверь квалифицированный ID в очереди фичи.

При подтверждённом расхождении используй [передачу очереди](operations.md#передача-очереди-обязательному-предшественнику).
