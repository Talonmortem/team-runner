# Улучшение процесса Team Runner

Дата: 2026-10-08. Статус: проект плана; реализация не начата.

Объём по умолчанию: подробно — идентичность проверяемой версии и проверка
постановки до dispatch; короткий маршрут, выбор проверок и метрики — следующие этапы.
Это предложение, а не изменение действующих правил или разрешение запускать цели.

## Основание

- `roles-and-rules.md` уже требует SHA + manifest грязного дерева, но также
  содержит безусловное требование проверки точного commit.
- `templates/impl-step.md` предполагает закоммиченные прошлые шаги;
  `templates/reviewer.md` предлагает diff только между BASE и HEAD.
- `templates/mkspec.py` проверяет заполнение placeholders, но не контракт задания.
- `runner_launch.py:dispatch_role` вызывает `child_run` до проверки структуры
  задания. Проверку нужно выполнить раньше любого создающего ресурсы вызова Orca.
- `engine.py:verify_item` проверяет трекинг, наличие отчёта и условия commit/clean;
  сопоставление принятого результата с frozen manifest пока не реализовано.
- `tracking.py:next_item` исключает completed, но не draft/planned.
  Поэтому этот план пока не добавляется в исполняемый Tasks.json.

## Этап 1. Однозначная передача и приёмка

Результат: implementer, tester, reviewer и координатор ссылаются на одну
проверяемую версию; неполное задание отклоняется до создания ресурсов Orca.

Ограничения: Python 3.11+, stdlib; существующие Context, snapshots и журнал effects;
один пишущий исполнитель; без автоматических коммитов, веток, replay и live smoke.
Исторические отчёты и снимки попыток не переписываются.

### P1. Контракты и согласование инструкций

Область: `roles-and-rules.md`, `GOAL_MASTER.md`, `worker-brief.md`, ролевые инструкции,
`templates/*.md`, README и `goal-runner.md` в затронутых местах.

- Заменить безусловные требования commit на требования snapshot-профиля.
- Идентичность версии: checkout/attempt + HEAD (может отсутствовать до первого
  коммита) + digest версионированного frozen manifest.
- Различать исходное состояние, предъявленную версию и версию после отчётных правок.
  Чужие исходные изменения фиксировать отдельно от изменений исполнителя.
- Reviewer получает сравнение исходного и предъявленного содержимого, включая
  staged, unstaged, новые и удалённые файлы; одного `git diff BASE HEAD` недостаточно.
- Зафиксировать JSON-схемы средствами stdlib и примеры валидных/невалидных данных
  для P2/P3. Не использовать разбор произвольного Markdown как проверку контракта.

Приёмка: правила допускают работу без коммита при соответствующем профиле;
require_commit/require_clean сохраняют своё значение; шаблоны не требуют
одновременно взаимоисключающих действий. Неподдерживаемая ситуация обозначается
явной ошибкой, а не неполной идентичностью или выдуманным SHA.

### P2. Frozen manifest и привязка доказательств

Зависит от P1. Область: небольшой модуль manifest, `engine.py`, шаблоны и точечные тесты.

- Формат manifest v1: identity попытки/checkout, исходный HEAD или null,
  область входов, отсортированные относительные пути, тип/режим и SHA256 содержимого,
  удаления относительно baseline, digest канонического документа.
- В область входят исходники, тесты, конфигурация и зависимости, влияющие на
  объявленные проверки. Новые файлы учитываются; runtime-артефакты и credentials
  не включаются автоматически. Исключения явные; изменение списка входов меняет digest.
- Symlink не позволяет незаметно читать за пределами checkout; внешние входы
  требуют отдельного явно объявленного контракта. Неподдерживаемые типы отклоняются.
- Заморозка создаёт проверенную копию входов в каталоге попытки. Приёмка tester
  и reviewer относится к этой копии; тестовые записи — в отдельных рабочих копиях.
  Изменение входов во время создания snapshot приводит к отказу и новой заморозке.
- Доказательства содержат manifest digest, роль/раунд, критерий, команду, cwd,
  exit code и путь к логу. Отсутствие обязательного результата или SKIP не даёт PASS.
- Приёмка сверяет доказательства и текущие предъявляемые входы с manifest.
  Только отчётные изменения вне этих входов не требуют повторного прогона.
- Хранение baseline и frozen-копий ограничено попыткой; существующие правила
  очистки тяжёлых артефактов применяются после приёмки, manifest/отчёты сохраняются.

Приёмка: одна версия даёт один digest; добавление/изменение/удаление входа меняет
его; чужая попытка, устаревший PASS, отсутствующий лог и изменившийся checkout
не принимаются. Покрыть чистое/грязное дерево, staged + unstaged одного файла,
untracked, удаления, symlink и отсутствие HEAD. Commit не создаётся как обход ошибки.

### P3. Проверка задания до dispatch

Зависит от P1; интеграция ссылок на manifest — после P2.
Область: `templates/mkspec.py`, CLI launch, `runner_launch.py`, snapshot контекста,
небольшой модуль проверки контракта и точечные тесты.

- Предлагаемый интерфейс: существующий Markdown `--spec` + JSON
  `--task-contract`. Генератор выдаёт согласованную пару; ручная подготовка разрешена.
- Контракт v1: роль, function/item/step, identity попытки/checkout, digest spec,
  права чтения/записи и разрешённые пути, критерии с ID, проверки с argv/cwd,
  зависимости, каталог артефактов, ссылки на входные документы и manifest при необходимости.
- Пустые зависимости допустимы явно. Для неприменимой проверки нужны причина
  и область применения; обязательные checks snapshot-профиля этим не отменяются.
  Для explorer/planner нужны результаты чтения/планирования, а не фиктивные тесты.
- Проверить типы/обязательные поля, пути, соответствие роли, ссылки критериев
  на проверки, существование входов и завершённость объявленных зависимостей.
  Структурная проверка не обещает оценить качество требований или тестов.
- Проверка выполняется в общем `dispatch_role` до `child_run`, task-create,
  terminal-create и worker-start, включая reuse. Невалидное задание не создаёт
  ресурсов и не переводит попытку в unknown/fenced.
- Сохранить неизменяемые spec + contract до effects; отправлять именно сохранённый
  текст. Request/reconcile используют прежнюю пару, без перечитывания изменившегося файла.
- Версию контракта зафиксировать в snapshot новых попыток. Старые попытки работают
  по прежнему контракту; retry без refresh сохраняет его, refresh выбирает новый.
  Для новой строгой попытки отсутствие контракта — ошибка, без тихого обхода.
- Прямые внутренние запуски coordinator/final orchestration отдельно перечислить
  при реализации: они не должны случайно требовать worker-поля или обходить
  обязательную проверку дочерних ролей.

Приёмка: валидное задание запускается один раз; ошибка возвращает поле и причину;
подмена spec/identity/manifest отклоняется; при отказе fake Orca подтверждает ноль
создающих вызовов. Старые snapshots, retry/reuse и unknown-recovery сохраняют семантику.

### P4. Интеграция и проверка этапа

Зависит от P2/P3. Синтетический checkout и fake Orca:
постановка → dispatch → изменение → freeze → tester/reviewer → приёмка.

- Успешные сценарии без коммита и с обязательным коммитом в тестовом репозитории.
- Отказ на неполном задании до Orca; отказ на изменении входов после проверок;
  отказ при доказательствах другой попытки; корректное продолжение старой попытки.
- Новые узкие тесты manifest/contract; `tests/test_mkspec.py`;
  затронутые Platform, LaunchAndStop, Configuration и Recovery/Reuse.
- Полный unittest discovery — один раз на финальной интеграции этапа, поскольку
  меняется общий запуск ролей. Browser — только если меняется UI/HTTP-контракт.
- Свежий reviewer по общей версии: identity, TOCTOU, snapshot-совместимость,
  отсутствие внешних effects при невалидном задании. Проверки только offline.

Этап завершён, когда P1–P4 приняты; README описывает форматы, ошибки и переход
старых попыток. До этого отдельный PASS helper-тестов не означает готовность этапа.

## Следующие этапы

| Этап | Предлагаемое изменение | Условие готовности |
| --- | --- | --- |
| 2. Короткий маршрут | Для малой задачи с ясными критериями — implementer и независимая проверка; explorer/planner при неопределённости. Критерии допуска зафиксировать в профиле попытки. | Сложные контракты, права, миграции и конкурентность сохраняют полный маршрут; причина выбора записана. |
| 3. Выбор проверок | Матрица «входы/инварианты → проверки»; промежуточные проверки по изменению, обязательный набор snapshot-профиля на финале. | Неизвестное влияние расширяет набор; обязательные проверки не исключаются; T1/T2 не дублируют прогон без причины. |
| 4. Метрики | Время до приёмки, приёмка с первого предъявления, причины возвратов, пропущенные дефекты; дополнить существующие категории расхода. | Повторные события не удваивают счётчики; неизвестный расход не ноль; отчёт по роли/функции и размеру задачи. |

После этапа 1 собрать данные нескольких сопоставимых задач. Изменять размер шагов
и состав ролей по результатам; автоматическую смену моделей по метрикам не вводить.

## Риски и границы

- Полнота manifest важнее хэша: пропущенный вход делает привязку доказательств ненадёжной.
- Копирование входов увеличит диск/время; объём и время заморозки измерить на fixtures,
  затем на отдельно разрешённом реальном сценарии.
- Старые попытки сохраняют прежние гарантии; их нельзя показывать как проверенные
  новым контрактом. Активные snapshots не мигрировать на месте.
- Новые жёсткие требования могут увеличить возвраты постановки. Отдельно учитывать
  эти отказы, не записывать их как дефекты implementer.
