# Команда пилота: роли и правила

Для goal-runner параметры runtime/profile/provider/model/effort задаёт снимок
`$TEAM_RUNNER_ATTEMPT/config.json`; он имеет приоритет над таблицами ниже и ролевыми defaults.
Запуск — `team-runner launch <role>`, чтение сообщений — `team-runner messages`.
Используй только CLI платформы; ручные launch/reuse/mailbox/monitor не применяются.


## Роли

| Роль | Агент | Модель / effort | Права |
|------|-------|-----------------|-------|
| coordinator / supervisor | Claude Code | claude-opus-5-5, high | Назначает задачи, принимает/отклоняет результат, сам проверяет diff |
| explorer | Codex | gpt-6-luna, xhigh | Только чтение, исходники не меняет |
| planner | Codex | gpt-6.1-sol, high | Только чтение; план с зависимостями, границами и критериями |
| implementer (standard) | Codex | gpt-6-luna, xhigh | Единственный пишущий исполнитель, только в текущей ветке |
| implementer (medium) | Codex | gpt-6.1-terra, xhigh | Выбор реализации внутри утверждённого контракта |
| implementer (complex) | Codex | gpt-6.1-sol, high | То же; межслойные контракты, конкурентность, права, аудит, миграции, риск HIGH (MODELS.md) |
| tester | Codex | gpt-6-luna, xhigh, отдельная сессия | Не меняет production-код; проверяет точный commit |
| final_reviewer | Codex | gpt-6.1-sol, high, свежая сессия | Только чтение, независимое ревью |
| tester_complex | Codex | gpt-6.1-sol, high | Самостоятельный T2 сложных задач после T1 PASS |
| final_reviewer_critical | Claude | claude-opus-5-5, high | Критические инварианты; свежая сессия |
| escalation | Codex | gpt-6.1-sol, high | Только консультант, свежая сессия |
| escalation_expert | Claude | claude-opus-5-5, high | Только эксперт-консультант, свежая сессия |
| completion_checker | Codex | gpt-6-luna, xhigh | Формальная сверка tracking и ссылок |

Все роли Luna — **xhigh** (явный выбор пользователя, GOAL_MASTER §«Роль координатора»); понижать effort
без нового указания пользователя нельзя. Исторические записи пилота (explorer/tester на medium) — факт,
они не переписываются. Значения `medium` в ролевых инструкциях исправлены на `xhigh` 2026-09-20
по указанию пользователя: таблица выше, `MODELS.md`, `roles/openai_explorer.md` и `roles/openai_tester.md`
согласованы между собой.

Подключения выбираются из настроек ролей. Глобальные конфиги и авторизация не меняются.
Таблица описывает шаблон «Текущие агенты». «Cloud.ru» и его резервы описаны в MODELS.md.
Класс standard/medium/complex утверждает координатор: standard — заданное локальное решение,
medium — выбор реализации в утверждённом контракте, complex — изменение критических инвариантов.
Исполнители выполняют предварительные тесты; независимую приёмку в Cloud.ru проводит GLM.
Резерв: `team-runner launch ROLE --variant reserve --reason "причина"`, всегда свежая сессия.
До замены подтвердить завершение/остановку предыдущего исполнителя и сверить неизвестные операции.
Резерв берётся только из снимка попытки; автоматической замены нет. Второе ревью — по решению координатора.

`worker-start --terminal` даёт supervised-владение:

Запускай роли через `team-runner launch`; читай `team-runner messages`.

## Общие правила

1. Источник требований — immutable context.json: instructions, requirements, профиль проекта и Tasks.json.
   Проектные правила имеют приоритет; новых бизнес-правил не придумывать. Неясность — ask координатору.
2. Worker выполняет только свою задачу. Не запускать subagents / multi-agent / скрытые команды внутри worker
   (полезные инструкции openai_explorer/implementer/tester/reviewer перенесены в спецификации задач).
3. Один пишущий исполнитель. Работа идёт в текущей ветке текущего checkout от зафиксированного
   base SHA; новые ветки и worktree не создаются без явной просьбы пользователя. Чужие
   незакоммиченные изменения в рабочем каталоге не трогать: перед стартом зафиксировать
   `git status` и список чужих файлов, после — проверить, что они не изменены.
4. Запрещено: push, deploy, destructive git (reset --hard, clean, checkout -- ., force, rebase чужого),
   изменение глобальных конфигов, операции с production-БД. PostgreSQL — только одноразовый локальный
   кластер/БД, созданные для проверки.
5. Не выводить секреты (DSN с паролями, токены, auth.json) в отчёты и логи.
6. Сообщение «готово» не является приёмкой. Приёмка — после отдельной сессии tester по точному commit
   и собственной проверки diff координатором. Незапущенная проверка = не пройдена.
7. Замечания возвращаются implementer как конкретные задания; пороги смены профиля — §«Возвраты и эскалация».
8. Каждый worker завершает работу ровно одним `worker_done` с `--outcome succeeded|failed`,
   указывает изменённые файлы и путь к отчёту.

## Возвраты и эскалация

Возврат — отклонённая передача результата на замороженной версии, а не отдельное замечание: раунд с девятью
замечаниями — один возврат. Координатор помечает причину: `defect`, `evidence`, `requirements` или
`infrastructure`, и ведёт счётчики на функцию и профиль в state.md (между dispatch и исправлениями).
Класс дефекта определяется нарушенным инвариантом, а не именем файла.

- Первый `defect`: воспроизведение, причина, регрессионная проверка — тот же implementer.
- standard (Luna) → complex (Sol): второй `defect`-возврат того же класса, третий `defect`-возврат любого класса,
  либо сразу — при обнаружении критического риска, пропущенного при выборе профиля.
- `evidence`: первый возврат — дополнить доказательства; второй на той же функции — остановить следующий шаг и
  проверить постановку/DoD. Если требования были явными и выполнимыми — Luna → Sol, иначе сначала исправить
  постановку. `infrastructure` и новые требования не считаются слабостью модели.
- После двух неудачных исправлений одного класса либо трёх `defect`-возвратов Sol — свежий
  `escalation` (Sol high). После одного безуспешного цикла «консультация → исправление → независимая
  проверка» — свежий `escalation_expert` (Opus high). После неудачи экспертного цикла — остановка
  прежнего цикла и пересмотр плана координатором. Если в immutable `$TEAM_RUNNER_ATTEMPT/config.json`
  `auto_continue_after_replan=true`, координатор сохраняет новый план, меняющий подход с учётом причины отказа,
  и продолжает исправление и независимую проверку в текущей попытке. Сам порог эскалации не является причиной
  `worker_done failed`. При false или отсутствии настройки — остановка и передача пересмотренного плана.
  Включение не отменяет приёмку, разрешения проекта и запрет replay unknown effects; конкретный внешний
  блокер или необходимое решение пользователя по-прежнему требуют остановки.
- Обе роли только анализируют и выдают конкретное задание; production меняет назначенный implementer.
  Координатор сохраняет управление. Замена недоступного/запрещённого Claude — по MODELS.md,
  с обязательной причиной в задании и отчёте, без изменения snapshot и без replay unknown effects.
- Пороги — стартовая политика; координатор пересматривает их по метрикам функций.
- Один класс — весь класс (решение пользователя 2026-10-07). Если находка относится к классу из
  `$TEAM_RUNNER_MATERIALS/defect-classes.md` или повторяет уже найденный класс, задание на fix требует обойти весь класс: таблица
  всех маршрутов или writers класса (источник списка, статус каждого, тест). Исправление одного места не
  принимается.

## Сессии и независимость

- Implementer: одна функция — одна роль implementer (решение пользователя 2026-10-07, заменяет «каждый шаг —
  новая сессия» от 2026-09-26). Каждая новая сессия заново читает ~10M токенов контекста, поэтому:
  - planner режет функцию на крупные шаги: один шаг — законченное логическое изменение на 1–3 часа работы
    (один или несколько коммитов). Соседние мелкие шаги в тех же файлах или по одной теме  объединяются в один dispatch; ориентир — не больше 6–8 шагов на функцию, включая тесты;
  - следующий шаг или fix может продолжить ту же сессию implementer, если профиль тот же и контекст сессии
    не выше ~50%: новый dispatch в тот же терминал (`team-runner launch --reuse`) со спецификацией шага;
  - новая сессия того же профиля с handoff из файлов (план, решения, отчёты прошлых шагов, `git diff`) — когда
    контекст выше ~50%, сессия упала или правило свежей сессии ниже требует её. Старые taskId/dispatchId не
    использовать;
  - ошибка «usage limit … remote compact task» означает переполненный контекст сессии, а не исчерпанную квоту:
    сразу передать шаг новой сессии.
- Контекст воркера :
  - задание ссылается на `$TEAM_RUNNER_MATERIALS/worker-brief.md` и `$TEAM_RUNNER_MATERIALS/defect-classes.md`, а не на этот регламент целиком;
  - основной план — до 800 слов с индексом отдельных карточек Ik (до 500 слов каждая): файлы, критерии K,
    классы C, решения, тесты и точные ссылки на полные приложения. Задание implementer включает только текущую
    карточку текстом (`$TEAM_RUNNER_MATERIALS/templates/impl-step.md` + `$TEAM_RUNNER_MATERIALS/templates/mkspec.py`).
    Правила полноты, исключений и выборочного чтения — worker-brief.md §«Объём документации и чтение»;
  - продолжение шага в той же сессии — `team-runner launch`.
- Tester: отдельная от implementer сессия, переиспользуемая между раундами одной функции; каждый раунд заново
  сверяет замороженный manifest и выбирает проверки по требованиям и diff; прежний PASS не переносится на
  изменившиеся входы. Если tester пропустил BLOCKER, найденный позже, — дать ему конкретный пробел матрицы;
  при повторном пропуске — новая tester-сессия.
- Раунд tester — два dispatch: T1 гейты (`$TEAM_RUNNER_MATERIALS/templates/tester-gates.md`: программный manifest preflight/postflight, проверки области item/stage из snapshot profile, миграции, readiness,
  frontend — только квитанции run_logged) и T2 собственные проверки, производительность, мутации
  (`$TEAM_RUNNER_MATERIALS/templates/tester-checks.md`). T2 standard идёт в той же сессии, если контекст ≤50%, иначе в новой.
  T2 complex — `tester_complex`, отдельный Sol после T1 PASS: самостоятельно проектирует проверки
  по требованиям, матрице рисков, frozen manifest и отчёту T1. Не повторяет полный T1 без причины.
  Reuse tester_complex — только та же попытка, функция, роль, настройки и измеренный контекст ≤50%.
  Для шаблона tester-checks укажи `--role tester_complex`; переход Luna → Sol всегда новая сессия.
- Свежая сессия нужна при смене роли или модели, новой независимой функции, повторении той же ошибки после
  явного объяснения и регрессионного теста, либо если после компакции контекст утрачен или противоречив.
  При ~70% контекста — checkpoint и оценка следующего шага, не обязательный перезапуск; если остатка не хватит
  на следующий этап — перезапуск на границе этапов с коротким handoff.
- Роль reviewer: planner фиксирует, координатор утверждает риск по MODELS.md. Авторизация, деньги,
  целостность данных, конкурентность, аудит чувствительных данных, исторические миграции и контракты
  этих инвариантов — `final_reviewer_critical` Opus high (в reviewer-шаблоне явно `--role final_reviewer_critical`).
  Неясный критический риск — Opus; остальное — `final_reviewer` Sol high. Всегда свежая сессия.
- Финальное ревью (решение пользователя 2026-09-26): свежий final reviewer обязателен для функций complex-профиля,
  для изменений схемы/миграций, прав, денег, аудита чувствительных данных и конкурентности. Для небольших
  функций standard-профиля и чисто UI-пунктов по отдельности — tester + браузер координатора, а их общее
  финальное ревью проводится на этапной приёмке .
- Финальный gate (решение пользователя 2026-10-07): после приёмки последнего шага tester (T1/T2) и свежий final reviewer
  (`$TEAM_RUNNER_MATERIALS/templates/reviewer.md`) запускаются последовательно по одному замороженному manifest. Полный набор проектных проверок запускает только
  tester; затем reviewer делает нужные узкие пробы в текущем checkout и окружении. Отдельный тестовый PG нужен только для проверок БД. Приёмка координатора — после обоих. После REJECT с
  исправлением следующий раунд снова проходит tester → reviewer; отдельный tester-раунд по отклонённой версии не нужен.
- Каждый reviewer dispatch — свежая сессия без истории implementer/tester и без reuse.
  Закрытие прежних замечаний проверяется по ссылкам на отчёты, manifest и фактическому diff;
  косметика/добавление доказательств не требует повторения полного T1 без причины.
  Reviewer сначала строит карту рисков по требованиям и полному diff, затем сверяет прежние
  находки и соседние пути.

## Доказательства готовности (implementer, до передачи tester)

- Planner до реализации задаёт матрицу: критерий → риск/инвариант → решающая проверка → ответственный.
- Между шагами — узкие проверки. Перед передачей законченной функции выполни команды из профиля и плана.
  Полные проверки независимо выполняет tester на замороженной версии; координатор проверяет решающие
  артефакты и браузер. Обязательный SKIP запрещает PASS; предсуществующий FAIL остаётся FAIL с владельцем.
- При изменении сериализации/DTO/режимов формы — контрактная проверка: тело из реального UI → настоящие
  handlers → ответ и сохранённое состояние. Моки, скопированные с UI, контракт не доказывают.
- Для HIGH-риска — направленные отрицательные проверки по применимости: отзыв прав во время управляемого
  ожидания, чужой владелец, аудит чувствительных полей, исторические данные, точность SQL-наборов; для UI —
  смена выбора во время загрузки, пагинация, 403/409, повтор, сохранение снимка.
- Browser smoke координатора — после первого сквозного UI/API-среза и после изменений затронутого пути; он не
  заменяет проверку implementer до передачи.
- Самопроверка по классам (решение пользователя 2026-10-07): перед передачей implementer прикладывает к отчёту
  отдельное полное приложение по `$TEAM_RUNNER_MATERIALS/defect-classes.md` — для каждого применимого класса список
  затронутых маршрутов/writers и доказательство. Основной отчёт содержит индекс и выводы, без копии приложения. Planner отмечает применимые классы в матрице, координатор кладёт ссылку на файл в
  каждую спецификацию implementer. Таблица без полного списка — возврат `evidence`.
- Мутации (решение пользователя 2026-10-07) — только для функций complex-профиля с риском в деньгах, правах,
  конкурентности или целостности БД. Для standard-профиля, чтения и UI отдельного этапа мутаций нет.
  Набор — до 12 мутантов по матрице рисков planner (критические инварианты и исправленные регрессии), одним
  шагом, не серией. STRUCTURAL засчитывается, если второй независимый слой (Go/SQL) ловит мутацию и это
  показано тестом. Только на изолированных копиях вне checkout.
- Промежуточное ревью (решение пользователя 2026-10-07): planner помечает в плане шаг `mid-review` — шаг-инвентаризацию
  (пути, writers, таблицы) или первый шаг с новым SQL-guard/миграцией. После его приёмки, до сквозных тестов, — короткое
  ревью выбранной по риску роли (MODELS.md) в свежей сессии (только чтение, ≤1 часа) по C6/C12 и полноте инвентаризации. 
- Новый SQL-guard или миграция с триггерами — задание implementer сразу требует C12: проверка только строк текущей
  транзакции и замер реальных команд на корпусе ≥10k (SQL до/после).
- Доказательства привязаны к tested SHA + manifest грязного дерева, команде, exit code и логу.

## Процессы, артефакты, сообщения

- RUN_STATE (`$TEAM_RUNNER_ATTEMPT/`) — единственное место runtime-отчётов, логов, БД и manifest;
  в репозиторий worker пишет только код/тесты своей задачи. В заданиях все пути даются абсолютными или явно
  от RUN_STATE.
- Запуск сервиса/PostgreSQL, ожидание и остановка — внутри одного harness с finally/trap и проверкой остановки
  (sandbox Codex может не видеть процесс в следующем вызове). Записывать PID/PGID, каталог, порт и владельца;
  перед остановкой сверять принадлежность. Невыполненная остановка блокирует успешную передачу и
  эскалируется координатору с точными данными; широкий `pkill` запрещён.
- Диск (решение пользователя 2026-10-07; RUN_STATE пункта рос до 110 ГБ):
  - обычные тесты идут в текущем checkout; временная копия затронутых исходников нужна только для мутаций. PG data и мутанты — внутри harness шага;
    worker удаляет их в конце шага, кроме замороженной копии, которую явно просил сохранить координатор;
  - после приёмки пункта координатор удаляет оставшиеся тяжёлые каталоги, сохраняя reports, logs, manifests,
    specs и state.md.
- Mailbox читает и транспортно подтверждает только runner. Координатор использует `team-runner messages` и `reply`; после обработки pending events — отдельный `team-runner events ack --dispatch DISPATCH --ids IDS`.
  Его heartbeat, ask и worker_done направляются по точной команде родительской преамбулы.
- Не повторяй неясную mutation. `reconcile` восстанавливает только доказанные исходы;
  `continue-operation` сохраняет request ID, argv и mailbox. Неизвестное владение блокирует stop/retry.
- Heartbeat — служебное сообщение; пользователю сообщаются смена этапа, результат или блокер.

## Формат отчёта worker

Отчёты, логи и manifest worker пишет в устойчивый каталог запуска
`$TEAM_RUNNER_ATTEMPT` (`logs/`, `reports/`, `manifests/`), а не только в `/tmp` и не
в TUI. Логи многословных команд создаёт `$TEAM_RUNNER_MATERIALS/run_logged.py run`. Итоговые документы команды и сводки
пилота хранятся в `$TEAM_RUNNER_MATERIALS/` репозитория (`$TEAM_RUNNER_MATERIALS/pilot/…`).

Worker создаёт краткий JSON для `python3 -m team_runner.worker_report` (схема в `--help`).
Helper добавляет роль, launch settings, task/dispatch и создаёт итоговый отчёт; ручной дубль не нужен.
Поля: outcome, summary, files_modified, checks (ссылки внутри попытки), issues, next_step.
Идентичность проверенного исходника и результаты команд остаются в приложенных evidence.

Правила заполнения:

- «Результат» — вердикт и одна-две строки по существу, без пересказа хода работы.
- «Проверки» — по строке на команду, данные берутся из квитанции `run_logged.py` (`CMD`, `EXIT`,
  `STDOUT`/`STDERR`). Лог указывается путём; содержимое логов и выдержки из них в отчёт не
  вставляются — при необходимости даётся готовая команда `run_logged.py show --log … --grep …`.
  Незапущенная проверка пишется как «не запускалась», а не опускается.
- Выполненные критерии отмечаются номерами из плана, а не пересказываются.
- Пустой раздел заполняется словом «нет»; пропускать разделы нельзя.
- Хэши артефактов — в manifest, в отчёт выносятся только при расхождении.

## Где что лежит

Общая реализация — установленный пакет team_runner; roles/templates/регламенты — внутри пакета.
При запуске неизменяемая копия общих материалов находится в $TEAM_RUNNER_MATERIALS.
Проектные инструкции, бизнес-правила, задачи, проверки и исторические отчёты остаются в checkout.
Runtime-логи и manifest — в $TEAM_RUNNER_ATTEMPT; секреты туда не записываются.

## Формальное завершение

completion_checker (Luna xhigh) сверяет статусы tracking, наличие и соответствие ссылок на отчёты,
идентификаторы задач и проверяемые версии; перечисляет пробелы. Не повторяет полный набор тестов,
не оценивает архитектуру и не принимает реализацию.
Код финальной проверки требует читаемый tracking каждой заявленной функции, completed всех пунктов
и функций, предусмотренные acceptance.md и goal-final-review.md; commit/clean — по профилю.
Неполный tracking или отсутствующий обязательный артефакт запрещает завершение.
Доказанность требований оценивают reviewer и координатор; универсального парсера Markdown нет.

При scoped checks дорогой stage gate следует после независимого review и исправлений подтверждённых blocker/high. Полный набор — только завершающий пункт этапа; legacy profile без scope сохраняет прежнюю семантику. Тяжёлые DB/mutation/review пробы получают host resource lock до PostgreSQL, без вложенных lock. PASS из истории требует новой проверки применимости и записи evidence; никакие старые исполняемые операции не импортируются.

## Быстрая безопасная передача
Worker завершает dispatch через `python3 -m team_runner.worker_report --input FILE --from HANDLE --task-id TASK --dispatch-id DISPATCH`.
Формат JSON: см. `--help` и worker-brief.md. Краткий результат плюс ссылки на подробные evidence; не переписывать журналы и метаданные вручную.
Координатор использует этот отчёт и приложения без второго пересказа. Проверки и бизнес-приёмка остаются его ответственностью.
Произвольный текст сообщений передавать через `python3 -m team_runner.orca_msg send --body-file FILE ...`; файл писать через quoted heredoc или API, без shell-подстановки текста.
