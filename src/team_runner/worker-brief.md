# Памятка worker (обязательна для каждого задания)

Короткая выжимка `$TEAM_RUNNER_MATERIALS/roles-and-rules.md` для Codex-воркеров. Задание ссылается на неё вместо полного регламента;
полный регламент читай, только если задание прямо называет его раздел.

## Правила
1. Требования — только из задания и файлов, на которые оно ссылается (ТЗ, план или карточка шага, решения). Новых
   бизнес-правил не придумывай: неясность — `orca orchestration ask` координатору.
2. Делай только свою задачу. Subagents, multi-agent и скрытые команды не запускай.
3. Работа в текущей ветке и checkout, без новых веток и worktree. Чужие незакоммиченные файлы не трогай: зафиксируй
   `git status` в начале и сверь в конце.
4. Запрещено:
   - push, deploy;
   - destructive git;
   - изменение глобальных конфигов;
   - production-БД.

   Тестовые сервисы — только изолированные экземпляры.
5. Секреты (DSN с паролем, токены, auth.json) — не в отчёты и логи.
6. Коммиты разрешены только при workflow.allow_commits=true; владелец — координатор. Progress.txt, Tasks.json, evidence/ и $TEAM_RUNNER_MATERIALS/ не меняй.
7. Ровно один `worker_done` с `--outcome succeeded|failed`, dispatch ID из задания, изменёнными файлами и путём отчёта.
   Если Orca его отклонит, последняя строка экрана — `REPORT COMPLETE`.

## Процессы и файлы
- **Артефакты** — отчёты, логи, manifest, копии, PG data, TMPDIR. Только в `RUN_STATE=$TEAM_RUNNER_ATTEMPT`, в
  репозиторий — только код и тесты задачи.
- **Команды** запускай напрямую, без `bash -c`. Длинные — через `python3 -m team_runner.run_logged run --label <имя> --run <run> -- …`.
  Логи читай `run_logged.py show --grep/--tail`, не целиком: так экономится контекст.
- **PG и сервер** запускаются и останавливаются в одном harness с trap. Порт проверь свободным (`ss -ltnp`), остановку докажи.
  `pkill` и kill по шаблону запрещены. Не можешь остановить — сообщи координатору PID и путь.
- **Контекст.** При ~80% контекста пиши checkpoint `RUN_STATE/reports/<отчёт>-checkpoint.md` (сделано / осталось / как
  проверить) и сдавай `worker_done --outcome failed` с пометкой checkpoint.

## Гейты передачи
- Выполни проверки из immutable context.json и карточки шага, с указанными cwd и argv.
- Коммиты и проверки определяются workflow/acceptance проекта. SKIP не означает PASS.
- Сохрани frozen manifest, exit codes и пути логов в каталоге попытки.

## Завершение и отчёт
- Создай компактный JSON через файл или quoted heredoc (`<<'JSON'`): `outcome`, `summary`, `files_modified`, `checks`, `issues`, `next_step`.
  `checks` — относительные пути к существующим evidence внутри попытки. Незапущенные проверки обозначь явно.
- `python3 -m team_runner.worker_report --input FILE --from HANDLE --task-id TASK --dispatch-id DISPATCH`
  с точными injected IDs сам создаст отчёт, добавит метаданные и отправит один `worker_done`. Не отправляй второй вручную.
  При неизвестном результате отправки сохрани ошибку и сообщи координатору: автоматический повтор запрещён.
- Основной текст — результат, проблемы, следующий шаг; подробные матрицы и инвентари — отдельные evidence со ссылками.
  Критерии отмечай номерами K. Логи не переписывай.
- Implementer прикладывает таблицу самопроверки по `$TEAM_RUNNER_MATERIALS/defect-classes.md`: класс → применимость → полный
  список маршрутов/writers с источником → доказательство. Таблица остаётся отдельным приложением, не дублируется в сообщении.
- Произвольный текст отправляй только `python3 -m team_runner.orca_msg send --body-file FILE ...`.
  Не вставляй текст в shell `--body`, backticks и `$()` могут выполнить команды.

## Объём документации и чтение
- Основной план — до 800 слов: scope, решения, зависимости, риски, критерии и индекс карточек. Карточка шага — отдельный файл до 500 слов; в задание включается только текущая карточка. Критерии и команды не терять ради лимита.
- Основной отчёт/inventory-summary — до 500 слов: результат, изменения, риски и точные ссылки. Полный список маршрутов/writers, матрицы и сырые результаты — отдельные приложения, без повторения одних данных в нескольких документах.
- Полнота проверки сохраняется: приложение содержит все применимые элементы, источник/команду получения и связь с критериями. Ограничивается пояснительный текст, а не число проверяемых элементов. Новые выводы сверяй с текущими исходниками и версией; ссылка не означает автоматический PASS.
- Читать сначала карточку и summary, затем указанные разделы/строки приложений по своей задаче. Не делать cat всего плана, inventory, истории отчётов или большого JSON. Полный охват reviewer сохраняется через индекс и последовательное чтение нужных разделов, без помещения всего приложения в один tool output.
- Существующий контракт не переписывать: дать ссылку + дельту + новые риски. Findings и решения имеют стабильные ID; после исправления обновить актуальное решение, историю хранить отдельно, а не добавлять повторные полные версии в конец плана.
- Если обязательное решение/сценарий не помещается, вынеси самостоятельный раздел в приложение и укажи его в индексе. Обоснованное превышение само по себе не вызывает новый dispatch, ревью или переписывание принятых документов.
