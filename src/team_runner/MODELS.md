Для goal-runner параметры runtime/profile/provider/model/effort задаёт снимок
`$TEAM_RUNNER_ATTEMPT/config.json`; он имеет приоритет над таблицами ниже и ролевыми defaults.
Запуск — `team-runner launch <role>`, чтение сообщений — `team-runner messages`.
Статические команды launch/reuse/mailbox/monitor ниже предназначены для запуска вне goal-runner.

## Проверка и критическое ревью

Planner фиксирует standard/medium/complex и критический риск; координатор утверждает до dispatch.
T1 всех задач выполняет tester. T2 standard может продолжить ту же сессию.
После T1 PASS сложной задачи отдельный tester_complex самостоятельно проектирует и выполняет T2:
требования, матрица рисков, frozen manifest и отчёт T1 обязательны в задании.
Полный T1 не повторяется без причины. Изменение проверяемых входов аннулирует PASS.
Reuse tester_complex допустим лишь в одной попытке, функции, роли и настройках, при измеренном контексте ≤50%.
Переход Luna → Sol всегда создаёт новую сессию.

final_reviewer_critical назначается для авторизации, денег, целостности данных, конкурентности,
аудита чувствительных данных, исторических миграций и контрактов, затрагивающих эти инварианты.
Неясный критический риск — Opus. Остальное — final_reviewer Sol high.
Reviewer всегда свежий, по тому же manifest, что tester. Периодичность из roles-and-rules сохраняется;
ревью каждого мелкого шага не добавляется.

Резерв запускается только решением координатора: `team-runner launch ROLE --variant reserve --reason "причина"`.
Настройки берутся из `reserves` снимка; отсутствующий резерв старой попытки не дополняется defaults.
Перед сменой исполнителя подтвердить завершение или остановку предыдущего; неизвестный результат
сначала reconcile. Резерв всегда получает свежую сессию; автоматического fallback нет.
В «Текущих агентах» резервы изначально пусты. Для добавления резерва настрой следующую попытку.
Второе ревью назначает координатор по риску и результатам первого.

## Выбор профиля implementer

- **standard** — локальная задача с заданным решением и проверяемым результатом, без
  изменения критических инвариантов; механическое изменение в нескольких слоях само по себе не требует complex.
- **medium** — выбор реализации внутри утверждённого контракта, без изменения критических инвариантов.
- **complex** — изменение межслойного контракта (SQL/API/UI), конкурентности и блокировок,
  авторизации/живых прав, аудита чувствительных данных, миграций с историей, либо риск HIGH от planner.
  Декомпозиция функции на шаги SQL/Go/UI не снижает её риск: профиль выбирается на функцию.
- Planner указывает профиль и конкретный фактор риска до первого dispatch; координатор утверждает.
- Исполнитель выполняет предварительные тесты; независимая приёмка остаётся за tester.

## Шаблон «Cloud.ru»

Только `opencode2`, provider `cloudru`, checkout внутри канонической границы `~/repo/sber`.
Выбор шаблона заполняет черновик; сохранение действует для следующих попыток.
Существующие снимки и выбранные настройки проекта не переключаются автоматически.

| Роль | Основная модель | Резерв |
|---|---|---|
| coordinator | Opus 4.8 | — |
| planner | Opus 4.8 | GPT-5.5 |
| explorer, implementer_standard, completion_checker | DeepSeek V4.1 Flash | Opus 4.8 |
| implementer_medium | Opus 4.8 | GPT-5.5 |
| implementer_complex | Opus 4.8 | GPT-5.5 |
| tester, tester_complex | GPT-5.5 | Opus 4.8 |
| final_reviewer, final_reviewer_critical | Opus 4.8 | GPT-5.5 |
| escalation | GPT-5.5 | Opus 4.8 |
| escalation_expert | Opus 4.8 | GPT-5.5 |

Координатор и планировщик: Opus — `high`, резерв планировщика GPT-5.5 — `xhigh`.
Все остальные роли, включая их резервы, — `medium`.
Лимит ответа Cloud.ru — 24 576 токенов, явно передаётся как `max_completion_tokens`; окно контекста не меняется.
Каждый терминал получает отдельное состояние TUI с выбранным вариантом, чтобы сохранённый
effort другого агента не переопределял снимок. Уже открытый OpenCode требует перезапуска.
Для Flash thinking включён явно. Предварительные тесты выполняет исполнитель;
независимую приёмку — отдельный тестер GPT-5.5 (резерв Opus 4.8). Исторические effort остаются читаемыми.
Запрошенный effort и подтверждённые наблюдения показываются отдельно: наличие параметра
в исходящем API JSON не доказывает применение уровня провайдером.

## Правила выбора

- Таблица задаёт package defaults для будущих попыток. Внешние TOML-конфиги, локальный каталог,
  saved overrides и текущие snapshots автоматически не мигрируются. Snapshot имеет приоритет.
- Роли на Luna и Terra работают с effort `xhigh`; понижать его без нового указания пользователя нельзя.
- Фактические model/effort/provider проверяются после запуска (`$TEAM_RUNNER_MATERIALS/orca_recover.py state`); профиль, причина
  выбора и переходы записываются в state.md запуска.
- Смена профиля (Terra → Sol → Opus) — новым запуском терминала: `--terminal` несовместим с `--model/--effort`.
- `openai_tester` нельзя запускать в той же сессии, где выполнялась реализация.
- `final_reviewer` нельзя запускать с историей planner/implementer/tester; ему передаются требования, diff и
  результаты проверок.
- `supervisor` — Claude Code/Opus, а не OpenAI-агент; его задача — надзор и координация, не замена независимого review.
- Замена gpt-6-luna на gpt-6.1-terra сделана без проектного бенчмарка: координатор ведёт метрики по функциям
  (принятие с первого предъявления, возвраты по классам, пропущенные HIGH/BLOCKER, время до приёмки) и
  сообщает пользователю о заметном ухудшении.
