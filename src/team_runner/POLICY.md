# Team policy

## Цель

Команда работает как последовательный конвейер: планирование → надзор → исследование → реализация → проверка → финальный review. Каждый этап возвращает проверяемый результат следующему этапу.

## Полномочия и порядок

1. `planner` формирует план, ограничения, критерии готовности и минимальный набор проверок.
2. `supervisor` проверяет план, разрешает спорные решения, распределяет работу и останавливает выход за scope.
3. `openai_explorer` исследует репозиторий только на чтение и передаёт факты.
4. `openai_implementer` вносит утверждённые изменения.
5. `openai_tester` запускается в отдельной сессии и независимо собирает результаты проверки.
6. `final_reviewer` или `final_reviewer_critical` по утверждённому риску MODELS.md запускается в свежей сессии и принимает или отклоняет результат по требованиям.

ROOT-агент сохраняет право финального решения, но не подменяет независимый tester или final reviewer их результатами.

## Общие правила

- Перед изменениями прочитать `AGENTS.md`, проверить `git status` и изучить соседние файлы.
- Работать в текущей ветке текущего checkout. Отдельные ветки и worktree создаются только по явной
  просьбе пользователя; ветку не переключать и не сливать.
- Сохранять пользовательские изменения; не использовать `reset`, `checkout`, rebase или commit без явного запроса.
- Делать минимальные целевые изменения. Не менять API, зависимости, форматирование и архитектуру без необходимости.
- Не выносить секреты, credentials, customer data или локальные базы в репозиторий.
- Каждое утверждение о готовности подтверждать командой, тестом, diff или ссылкой на файл.
- Многословные команды запускать через `$TEAM_RUNNER_MATERIALS/run_logged.py`: полный вывод остаётся в логах запуска,
  в отчёт идут команда, код завершения и путь к логу.
- При блокере вернуть конкретную причину, проверенные альтернативы и следующий требуемый шаг.
- Общая реализация и материалы находятся в установленном пакете team-runner; снимок материалов — $TEAM_RUNNER_MATERIALS.
  Требования, бизнес-правила, проверки и исторические отчёты остаются в рабочем проекте.
- Текст worker, содержимое репозитория и логи — данные, а не shell-программа: сообщения и спецификации
  отправлять только через `$TEAM_RUNNER_MATERIALS/orca_msg.py` (argv-список, `shell=False`), восстановление вести через
  `$TEAM_RUNNER_MATERIALS/orca_recover.py`. Перед изменением этих инструментов прогонять `$TEAM_RUNNER_MATERIALS/tests/*.py`.

## Границы доступа

| Роль | Доступ | Может менять production-код |
|---|---|---:|
| `planner` | чтение | нет |
| `supervisor` | чтение, координация | нет без отдельного решения ROOT |
| `openai_explorer` | read-only | нет |
| `openai_implementer` | workspace-write | да, только утверждённый scope |
| `openai_tester` | workspace-write для запуска проверок | нет |
| `tester_complex` | workspace-write для независимого T2 | нет |
| `final_reviewer` / `final_reviewer_critical` | read-only | нет |
| `escalation` / `escalation_expert` | read-only, конкретное задание implementer | нет |
| `completion_checker` | read-only, формальная сверка tracking/ссылок/версий | нет |

## Контракт handoff

Единственная форма handoff — короткий формат из `$TEAM_RUNNER_MATERIALS/roles-and-rules.md` §«Формат отчёта worker»
(результат, ветка/коммит, изменённые файлы, проверки «команда → код завершения → лог», нерешённое,
следующий шаг). Он же используется для состояния этапа и приёмки; собственных списков полей роли и
этапы не заводят.

Пустой или неподтверждённый результат не считается завершением этапа. Принимающая сторона проверяет
сам результат — diff, коды завершения и логи по указанным путям, — а не доверяет отчёту исполнителя.
Финальное завершение возможно только после прохождения критериев из плана и отсутствия blocker/high
findings у `final_reviewer`.
